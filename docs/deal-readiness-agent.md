# Deal-Readiness Agent — AI-suggested questions between Manufacturer & Buyer

> **Status:** Planned, not yet scheduled. This document is the implementation brief for a
> Claude-powered agent that analyzes a manufacturer's and a buyer's profiles and proposes
> role-specific questions to close gaps between them, surfaced inside the existing in-app
> conversation. WhatsApp is a later delivery channel, not part of this phase.

## 1. Goal

When a manufacturer and a buyer are in a conversation (already created when a buyer
"expresses interest" on an offer), give each party a short, tailored list of **questions
worth asking the other side** — generated by a Claude agent we control (we feed it the data
and the instructions). The agent **proposes only**; a human always reviews and sends.

Example: the buyer should ask *"How many pallets can you supply per shipment?"*; the
manufacturer should ask *"Which GCC channels are you buying for — retail, foodservice, or
online?"*. Each list is specific to that role and tied to a real gap or missing field.

## 2. Scope & sequencing

| Phase | What | Status |
|---|---|---|
| **Phase 1 (this plan)** | In-app "AI-suggested questions" panel fed by a Claude agent. | To build |
| Phase 2 (later) | WhatsApp as an *optional delivery channel* for the same `Question[]`. | Separate plan |

WhatsApp is **deliberately excluded** from this phase. The agent output (`Question[]`) is
channel-agnostic, so Phase 2 becomes a thin delivery layer (see §8).

## 3. Architecture (Phase 1)

```
Conversation (buyerAccountId, manufacturerAccountId, [cardId?])
        │
        ├─ resolve both profiles:  BuyerProfile  +  ManufacturerProfile
        │                            (+ linked OpportunityCard if present)
        ▼
   buildPrompt(OUR_TEMPLATE, { buyerProfile, manufacturerProfile, card })
        │   └─ profile text wrapped in wrapUntrusted()  (untrusted content)
        ▼
   Claude (claude-haiku-4-5)  ──►  JSON  ──►  jsonrepair  ──►  parse
        │
        ▼
   { buyerQuestions: [{text, gap}], manufacturerQuestions: [{text, gap}] }
        │
        ▼
   API response  ──►  ConversationsPanel renders per-role lists
```

**No persistence in Phase 1.** Suggestions are generated **on demand** when a conversation is
opened (and on a manual "Regenerate" click). This means **no DB migration** and **no new PII
storage** — nothing extra to cover in `exportMyData` / `deleteMyAccount`.

## 4. Backend — new endpoint

```
POST /api/conversations/:id/suggest
Auth: requireAuth (either participant)
```

**Steps**
1. Load the conversation; verify the caller is one of the two participants (403 otherwise).
2. Resolve the two participant accounts → their `BuyerProfile` / `ManufacturerProfile`.
   (Verify during build: conversation→accountIds→profiles. If a profile is missing, treat as
   empty rather than failing.)
3. (Optional) Resolve the linked `OpportunityCard` for offer context.
4. `buildPrompt(...)` → Claude call (reuse the existing `@anthropic-ai/sdk` client + model
   `claude-haiku-4-5-20251001`).
5. Parse with `jsonrepair` (same pattern as `claudeMatch.ts`) and validate the shape.
6. Return `{ buyerQuestions, manufacturerQuestions }`.

**Response schema**
```ts
interface SuggestedQuestion { text: string; gap?: string }
interface SuggestionsDto {
  buyerQuestions: SuggestedQuestion[];        // questions the BUYER should ask the manufacturer
  manufacturerQuestions: SuggestedQuestion[]; // questions the MANUFACTURER should ask the buyer
}
```

Add the DTO to `packages/shared` (single source of truth, like the other DTOs).

## 5. Backend — the agent (`apps/api/src/lib/dealReadiness.ts`)

New module, mirroring `claudeMatch.ts` / `claudeScore.ts`:
- `generateSuggestions(input): Promise<SuggestionsDto>`.
- Wrap each profile field in `wrapUntrusted` from `lib/promptSafety.ts` (profiles are
  user-supplied → treat as untrusted to prevent prompt injection).
- Use `jsonrepair` on the raw response before `JSON.parse` (Claude output is frequently
  imperfect JSON — don't hand-roll cleanup).
- Keep the **instruction template in our code** (this is *our* agent — we tune the brief).

**Draft prompt (tunable)**
```
You are a B2B GCC market-entry deal-readiness assistant.
Given a MANUFACTURER profile and a BUYER profile (and optionally the offer they are
discussing), identify concrete gaps that would block, delay, or clarify a deal.

For each gap, write a single, specific, answerable question that one party should ask the
other. Questions must reference real mismatches or missing fields (certifications, capacity/
MOQ, payment terms, lead times, target channels, delivery geography, distribution rights,
Halal/SFDA status, etc.). Do not invent facts; ask to confirm.

Return STRICT JSON only:
{
  "buyerQuestions":        [ { "text": "...", "gap": "..." } ],  // what the BUYER should ask the manufacturer
  "manufacturerQuestions": [ { "text": "...", "gap": "..." } ]   // what the MANUFACTURER should ask the buyer
}
```

## 6. Frontend — UI in `ConversationsPanel`

File: `apps/web/src/features/conversation/ConversationsPanel.tsx` (add a sibling component,
e.g. `SuggestedQuestions.tsx`).

- A collapsible **"AI-suggested questions"** section above/beside the message thread.
- The viewer sees **their own role's** list as primary ("Questions for you to ask").
  Each item has a one-click **"Add to thread"** that inserts the text as a draft message
  (editable before send) — the human always sends.
- A toggle reveals the **other party's** suggested questions (so each side can anticipate
  what they'll be asked). *(Open question — see §9.)*
- "Regenerate" button re-calls the endpoint (loading + error states).
- New API call: `fetchSuggestions(conversationId)` in `apps/web/src/lib/api.ts`, typed from
  the shared DTO.

## 7. Data model notes

- **Phase 1: no schema change.** On-demand, ephemeral generation keeps it migration-free —
  important given the `db:migrate` reset guard in CLAUDE.md (never run `db:migrate` against
  Supabase; only `db:deploy` for additive changes).
- **If persistence is later wanted** (history across refreshes, audit): add a
  `ConversationSuggestion` table (conversationId, role, text, gap, createdAt) via `db:deploy`
  (additive, safe). Decide later; not required for v1.

## 8. Future: WhatsApp delivery (Phase 2, out of scope here)

The `Question[]` from Phase 1 is channel-agnostic, so Phase 2 is mostly a delivery layer:
- One platform **WhatsApp Business Account (WABA)** number (Meta Cloud API); each business
  does **not** need its own WABA.
- Opt-in + **GDPR consent** checkbox specifically for WhatsApp; Meta becomes a processor of
  phone numbers + message content.
- Platform number delivers new messages + AI suggestions to each party's phone; replies via
  **webhook** are written into the same in-app conversation thread (in-app = system of record).
- **24-hour service window:** free-form replies only within 24h of the user's last message;
  outside it, re-open with a **pre-approved template** (costs per message).

## 9. Open questions to settle before build

1. **Language:** English only, or also FI / AR? Affects the prompt and possibly the model.
2. **Other-party visibility:** show each side the *other* party's suggested questions, or
   strictly per-role? Recommend: show own role by default, with an opt-in toggle.
3. **Model:** `claude-haiku-4-5` (fast/cheap, already configured) vs Sonnet for higher-quality
   questions. Recommend Haiku first; easy to upgrade.
4. **Card context:** is the conversation reliably linked to the opportunity card? Verify the
   `Conversation` schema during build; treat as optional context.

## 11. Risks / constraints

- **Prompt injection:** profile text is untrusted — always wrap in `wrapUntrusted`
  (`lib/promptSafety.ts`) before it reaches the model.
- **JSON robustness:** rely on `jsonrepair`, never hand-rolled parsing.
- **GDPR:** keep Phase 1 ephemeral (no new stored PII). Revisit before Phase 2 (WhatsApp).
- **No migration against Supabase:** Phase 1 is migration-free by design; any future table uses
  `db:deploy` only.
